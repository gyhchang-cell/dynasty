# mcPvPmax 开发规则

## 用户明确要求（2026-10-27）

- 已经成功的版本是后续优化的基线。每次只在对应场景已验证的实现上做小幅、目的明确的调整；不得为了极端情况把正常搭路的速度、稳定性或连贯性改坏。
- 优先参考抖音作者“ikun是小菜”。需要研究动作时实际查看连续第一人称片段、逐帧记录时序，再对照本地录像和日志。不能用抽帧数量代替实际研究，也不能把视频看不出的按键、角度、落地状态或延迟当成已知事实。
- 微调不是限制必要修复的行数或规模。必须解决已复现问题；需要调整逻辑时应调整，以同场景证据检验效果，不把“改得少”作为完成标准。
- 一次实验只验证一个行为变化，记录基线版本、改动原因、适用场景、速度／稳定性／连贯性对比。实验退步就撤回该变化，不在退步版本上继续堆叠调整。
- 斜平、斜上均须连贯。每轮停稳、再回头补块、反复重建助跑不能算最终成功。异常保护停止与未掉落的短测，均不能冒充连续通过。
- 正常 R 松开要完成当前一跳、落稳并回正。失焦或读数失效仍要释放输入。
- 正常点击优先 15–18 CPS，稳定时可降低；本开发分支不启用 20+ 突发。不得用额外点击掩盖错误落点或破坏已有 CPS 约束。
- 未经同场景应用 R/T 入口对比验证的实验只留在 `.build/candidates/`。不覆盖桌面或 `dist` 的成功版本，不修改原有权限。导出名保持 `mcPvPmax`。
