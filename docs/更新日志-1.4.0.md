## ① 「进其他维度崩服」的真正根因：盔甲架没有攻击力属性

崩溃日志的关键三行（`crash-2026-09-13_18.04.44-server.txt`）：

```
java.lang.IllegalArgumentException: Can't find attribute minecraft:generic.attack_damage
    at net.minecraft.world.entity.ai.attributes.AttributeSupplier.getValue(AttributeSupplier.java:21)
    at net.minecraft.world.entity.LivingEntity.getAttributeBaseValue(LivingEntity.java:1843)
    at com.dynasty.DynastyDimensionDifficulty.onJoin(DynastyDimensionDifficulty.java:77)
```

`DynastyDimensionDifficulty` 在 `EntityJoinLevelEvent` 里给每只进入世界的怪按维度加难度，
其中读了一次**攻击力基础值**。问题在于：**并不是所有生物都有攻击力属性** ——
原版 `EntityType.ARMOR_STAND`（盔甲架）用的是

```java
DefaultAttributes: .put(EntityType.ARMOR_STAND, LivingEntity.createLivingAttributes().build())
```

而 `LivingEntity.createLivingAttributes()` 只有 **生命 / 抗击退 / 移速**，**没有攻击力**。
`AttributeSupplier.getValue()` 在缺属性时**直接抛 IllegalArgumentException**。

于是链条是：**区块里有任意一个盔甲架**（创造模式摆装备、展示盔甲最常见的东西）
→ 区块升级为 FULL 状态、实体反序列化
→ 我们的 `onJoin` 读攻击力 → 抛异常 → **服务端主线程当场崩**。

而「进入其他维度」只是触发条件 —— 那一瞬间恰好加载了带盔甲架的区块，
所以以前表现为「一进天朝 / 地府 / 九霄就崩」，而且换维度偶尔能不崩，极难定位。

**修法（结构性）**：

* 新增 `com.dynasty.DynastyAttributes`：`instance() / base() / value()` 先
  `AttributeMap.hasAttribute()` 检查，取不到就返回 null / 默认值，**永不抛异常**；
  `DynastyDimensionDifficulty` 全程改用它（读不到攻击力就只加血，不报错），
  并额外套一层 try/catch + 「同一种实体只提示一次」的日志；
* `DynastyBossAI.damage()` / `DynastyBosses` 火焰爆发里读攻击力的地方一并改走安全访问；
* `verify_entities.py` 增加**属性自检**：注册了实体就必须在 `EntityAttributeCreationEvent`
  里注册属性，且属性表必须含攻击力与生命（以后再加实体就不会踩这个坑）。

**顺带修掉一个「一直没生效」的老问题**：`DynastyAttributeCaps` 用反射改
`RangedAttribute.maxValue` 来解除攻击力/生命上限，但字段名在**生产环境是 SRG 名**
（`f_22313_`），只试 `maxValue` 必然失败 —— 日志里一直在刷「无法解除属性上限」。
现在改成：按名字试 → 失败就**扫描所有 double 字段**，并且写完用
`getMaxValue()` + `sanitizeValue()` **验证真的生效**，不生效就还原原值（不会留下 min>max 的坏状态）。

## ③ Boss 机制（新系统）

（第一次击杀每个 Boss/神兽额外给功名 + 主题材料，一种一次）。

## ① 崩溃根因（两类，全部修掉）

### A. 天境 / 地狱 / 九霄：`Feature order cycle found`

```
IllegalStateException: Feature order cycle found, involved sources: [... dynasty:jade_forest]
（另一次是 dynasty:soul_river）  Exception generating new chunk
```

根因：上一轮我把建筑挂到了 **Forge 的 biome modifier（add_features）** 上。
修饰器是在运行时注入特征的，**biome JSON 里看不到** —— 所以我的自检脚本
`verify_feature_order.py` 只看得见静态列表，**根本查不到这些注入的特征**，

**换思路（结构性修法）**：**取消所有「加建筑」的修饰器**，建筑只走一份
**静态特征表**（`fix_building_placement.py` 按唯一的 `CANON` 顺序写进每个群系的 stage 4）。

### B. 九霄（客户端）：`entityrenderer is null`

**再加一道自检**：`tools/art/verify_entities.py`（已接进导出）——

### 连锁挖矿怎么调（Vein Mining）

游戏目录里会生成 `config/veinmining-client.toml` 与 `veinmining-server.toml`：

| 想要的效果 | 改哪里 |
| --- | --- |
| 想「潜行才连锁」 | `veinmining-client.toml` → `activationState = "CROUCHING"` |
| 想「按键才连锁」 | `activationState = "HOLD_KEY_DOWN"`，再去「选项 → 控制」绑按键 |
| 想让连锁范围更大 | `veinmining-server.toml` → 调大 `maxBlocksBase` / `maxBlocksPerLevel` |
| 想只连锁矿石不连锁原木 | `veinmining-server.toml` → `blocksList` 删掉 `#minecraft:logs` |

（`maxBlocksBase` 是「没附魔时的上限」，把它调大就能在没附魔的情况下也连锁。）

## 第八轮：Embeddium 与「Embeddium 选项」互相冲突

第二次修复后又起不来，这次的崩溃报告写着：

```

```

也就是 **Embeddium 0.3.31 在元数据里明确声明「不兼容 TexTrue's Embeddium Options」**

# 追加更新（同一版 1.4.0 · 第二十二轮）：任务不再全卡死 + 地府重做 + 出生点/命名/数值

这轮按玩家的 8 条反馈逐条改。

## ① 任务不再「一条条卡死」，只留必要的锁

以前每条任务都挂着上一条（`接上一条`的兜底规则），玩家得按顺序一条条点。
现在前置只剩三类**真正必要**的：

| 保留的锁 | 说明 |
| --- | --- |
| 配方材料 | 要造巨阙重剑就必须先有玉剑 —— 这是游戏本身的逻辑 |
| 章节入口 | 只有每章**第一条**任务接上一章末尾，保证章节按顺序推进 |
| 剧情门槛 | 手写的 `extra`：Boss 信物、官阶、维度等（如玄天钺要龙帝玉玺） |

自动兜底的「接上一条」整条规则**删掉**了：前置从 589 条降到 **409 条**，
图鉴 / 饰品 / 收藏类任务现在想先做哪个都行。

顺带把排布和前置**解耦**：`layout_lines()` 只按「线」排（一条线一行、横着排、整章 y=0 居中），
所以放宽锁定不会把版面搞乱，收紧也不会。

## ② 传送落点不再掉进基岩层 / 岩浆

以前用 `getHeight(MOTION_BLOCKING_NO_LEAVES)` 直接取高度：在有基岩顶棚的维度会把人放到顶棚上，
在岩浆海上方会把人生成在岩浆里 —— 就是「出生点在底部基岩层」。

现在 `DynastyPortalBlock` 会**从高处往下扫，找一块能站人的地面**：

* 脚下必须是实心方块、不能是液体（岩浆不算地面）；
* 身体两格必须是空的、没有液体；
* 区块没加载先加载；
* **实在找不到就铺一个 3×3 石台**，保证一定落在陆地上。

## ③ 地府重做成真正的新维度 + 地狱的生物

地府以前是「原版地狱的复制品」：基岩顶棚 + 一望无际的岩浆海 + 黑石。现在：

| 顶棚 | 基岩顶棚（`has_ceiling`） | **没有顶棚**，抬头是暗色星空 |
| 天象 | `the_nether`（地狱红雾） | **`the_end`**（暗色星空） |
| 岩浆海 | y=32 一整片岩浆 | **没有岩浆海**（只留零散的岩浆泉 / 岩浆湖） |
| 高度 | y 0~256 | y **-64~320**（和帝陵的落点对齐） |
| 地表 | 下界岩 | **黑石**；忘川一带铺灵魂土 |
| 生物 | 只有王朝小怪 | **+ 烈焰人 / 恶魂 / 岩浆怪 / 僵尸猪灵 / 凋灵骷髅** |

地狱的产出（石英、萤石、灵魂沙、远古残骸、烈焰棒、恶魂之泪、岩浆膏）现在全都能在地府拿到，

# 追加更新（同一版 1.4.0 · 第二十一轮）：任务书排版重做 + 弓系分支 + 饰品分类

这轮全部对着玩家的排版反馈改：任务离得太远、饰品图鉴挤成一竖列、一章的链子全堆在下面、
七/八/九章一条线横着走、兵器谱只有一把弓。

## ① 排版参数与「一竖列」的根因

| 项目 | 以前 | 现在 |
| --- | --- | --- |
| 同一条链上相邻任务 | 2.0 格 | **1.5 格** |
| 两条链之间 | 再加 2.0 格（合计 4.0） | 再加 1.0 格（合计 2.5） |
| 垂直定位 | 全部从 y=0 一路往下堆 | **整章以 y=0 居中**（上下各占一半） |

**「饰品图鉴 38 个任务排成一竖列、排到 y=85」的根因**：前置推导的规则是
「配方材料也在任务书里 → 连成前置」，而图鉴这种章的配方材料**全在别的章** →
章内一个前置都连不上 → 38 个任务全被当成「孤立的根」→ 每个根占一行往下堆。

修法：兜底规则从「**完全没有前置**才接上一条」改成

# 追加更新（同一版 1.4.0 · 第二十轮）：修掉「打开任务书崩溃」+ 再补 10 套盔甲 + 10 件饰品

## ① 崩溃根因：任务前置图里有环 → FTB 无限递归

反馈是「一打开任务书就崩」，崩溃报告写得很清楚：

```
java.lang.StackOverflowError: mouseClicked event handler
  at dev.ftb.mods.ftbquests.quest.Quest.isVisible(Quest.java:810)
  at dev.ftb.mods.ftbquests.quest.Quest.lambda$isVisible$33(Quest.java:810)   ← 自己递归自己
```

FTB 判断「这个任务该不该显示」时会沿着前置一路递归。**前置里只要有环，它就一直转到栈溢出**。
用强连通分量一查，确实有 3 个环：

| 环 | 成因 |
| --- | --- |
| 金币 ×4 ⟺ 银币 ×16 | 币种互兑配方（金币↔银币 两条配方互相指） |
| 龙币 ×4 ⟺ 玉币 ×4 | 同上 |
| 青铜剑 → 兵器图纸 → 竹简 ×4 → 青铜剑 | 跨章配方：第一章的武器要第二章的图纸，图纸又要第一章的竹简 |

第十九轮加的「按配方推导前置」是按**配方里的材料**推的，双向配方和跨章配方就会互相指成环；
而当时的去环代码是**按章**跑的，看不见跨章的环 —— 这就是漏网的原因。

**修法**：改成**全局建图 + 只删回边**：

1. 先把所有前置算完（允许跨章、允许往前指）。
2. 整张图 DFS，遇到指向「正在递归栈里」的节点就是回边，删掉它。
3. 结果：450 条前置里**只删 4 条**，其余跨章前置全部保留
   （对比：用「凡是指向后面的就删」会白丢 19 条）。

**自检补上了这条**：`verify_ftbquests.py` 现在跑**真正的环检测**（DFS + 递归栈），
并且知道「某条配方前置如果加上去会成环，那它必须被删掉，不算问题」。
以后谁改出环，导出的第一时间就会红。

之前是按我手写的排列顺序串链，所以会出现**顺序颠倒**（比如先要求做成品、再要求收材料）。
现在生成器会读**数据包里的 149 条配方**，自动推出「成品 → 材料」关系：

```
要交出「青铜剑」→ 前置 = 铁剑 / 青铜锭×4 / 兵器图纸（配方里的材料）
要交出「龙鳞靴」→ 前置 = 玉靴 / 龙鳞 / 龙晶 / 兵器图纸
```

也就是说：**材料任务一定是成品任务的前置**，逻辑天然成立，不再依赖我手写顺序。
击杀 / 维度 / 成就 / 掉落类任务没有配方，则接本章上一条，保证不会变成点不到的孤岛。

# 追加更新（同一版 1.4.0 · 第十四轮）：修好「任务之间没有链条线」

## 真凶找到了：任务 id 的写法让 FTB 解析失败

FTB Quests 内部用 **`Long.parseLong(id, 16)`（有符号）** 解析任务 id —— 反编译确认：

```
invokestatic java/lang/Long.parseLong:(Ljava/lang/String;I)J
```

也就是说 id 的**首字符必须是 0~7**（即数值不能超过 `0x7FFFFFFFFFFFFFFF`）。
而我之前用的是：

```snbt
id: "d700000000000000"     // 首字符 d，高位是 1 → parseLong 抛异常
dependencies: ["d700000000000000"]   // 于是前置解析不到 → 不画连线
```

任务本身还能显示（当作各自独立的方块），但**所有前置关系都失效了** —— 表现出来就是
「任务一个个分开摆着、没有条连过去、看不出先做哪个」。

**修复**：id 生成改成安全区间的 16 位十六进制，且各类型首字符区分开：

| 类型 | 旧 | 新 |
| --- | --- | --- |
| 任务 | `d7xxxxxxxxxxxxxx` ❌ | `1xxxxxxxxxxxxxxx`（`1` + 15 位十六进制） ✅ |
| 任务目标 | `daxxxxxxxxxxxxxx` ❌ | `2xxxxxxxxxxxxxxx` ✅ |
| 奖励 | `dbxxxxxxxxxxxxxx` ❌ | `3xxxxxxxxxxx` + 2 位 ✅ |
| 章节 | `d0xxxxxxxxxxxxxx` ❌ | `4xxxxxxxxxxxxxxx` ✅ |

## 校验（新增了专门脚本）

```
任务数: 156 | id 数: 156
依赖总数: 160 | 高位为 1 的非法 id: 0        ← 全部可解析
指向不存在任务的依赖: 无 OK                  ← 160 条前置全部指向真实任务
```

现在 FTB 任务书里会画出完整的**前置连线**：做完的显示完成态（√），
没做完的显示锁定态（灰色锁），从章首任务向下分叉到各条支线，一眼就知道该做哪个。

> 注意：id 变了，**旧存档的任务进度会重置**（任务数据本身都在，重新点亮即可）。

## 验收

* `./gradlew build` / 导出 / 自检通过（63 jar）；三份整合包重新生成并同步
* 实例内抽查：`id: "1000000000000027"` ← `dependencies: ["1000000000000026"]` 等链条已就位

# 追加更新（同一版 1.4.0 · 第十三轮）：修掉「一章只看到一个任务」+ 一章多条支线并行

## ① 找到并修复了「后面每章只看到一个任务」的真凶

**原因**：树形排布在算「本章根节点」时只认「没有任何前置」的任务。
可是每章的章首任务都挂在上一章末尾，于是**除第一章以外，所有章节都找不到根**，
整章的坐标全部被塞进 `(0,0)` —— 在任务书里看就是「一堆任务叠在一个点上，只看得见一个」。

**修复**：根节点判定改成「前置都在本章之外」，每个章节都能正常铺开：
```
修复后 dynasty_c3.snbt：x 0 → 14.3，y 出现 10 个不同分层（原来是 25 个任务全在 x=0,y=0）
```

## ② 一章多条支线同时发展（学愚者那种任务界面）

* 每章 = **1 个章首任务 + 2~4 条并行支线**，支线起点都挂在章首上
  → 一进这一章，好几条线同时亮，可以按自己喜好挑着做
* 支线长度**故意不一样**（用 4 组不规则花纹轮转），所以画面是分叉的树枝状，
  不是「方阵」；每条支线还横向错开 0.35 格，避免排列死板
* 章与章之间仍然连着（章首 ← 上一章末尾），进度不会乱

各章铺开后宽度：第一章 x 0~18、第三章 0~14.3、其余 8~12（原来全是 0）——在一屏里看得全。

## 验收

* `./gradlew build` 通过；156 条任务引用校验「问题项：无」；自检通过（63 jar）
* 三份整合包重新生成，四处 mods + config 同步；实例内 11 章 156 条，坐标已正常铺开

# 追加更新（同一版 1.4.0 · 第二十轮）：任务书排版收紧 —— 支线不许拉长、任务不许离中心太远

玩家反馈：放射章 / 枝干章的支线一路往外拉，越走越远，得一直拖屏才找得到后面的任务。
这次把「几何」本身上了约束（不再靠一支一支手调）：

## ① 放射（fan）改成「到半径上限就绕着中心转」

* 半径上限 `R_MAX = 8.5` 格：散到这个距离后**不再往外拉**，多出来的节点改沿圆弧绕中心转
  （`BEND_DEG = 13°` / 每多一格）→ 支线可以继续发展，但离中心的距离永远 ≤ 8.5 格
* 主线（章首那条）也从中心向左散，同样受半径上限约束

## ② 枝干（tree）的支线改成「散开之后就平着走」

* 主干一段最多 8 个（`MAX_RUN`），超了折到下一行，不再一根主干横穿十几次格
* 支线不再一路往上/往下长，而是上下分层**平铺**（一层最多 16 格 `TREE_WIDTH`），
  一层放不下就再往外一层 —— 整章是扁的，不是竖的

## ③ 横排 / 竖排：超长的链子就地折行 / 折列

* 横排一层按宽度装箱（`PER_BAND` 个节点位），好几条短线共用一层 → 不再「十几层高」
* 竖排一列最多 10 个（`MAX_COL`），超了在右边紧挨着折一列；列距收紧到 `COL_PITCH = 1.75`

## ④ 自检加了一条硬指标

`verify_ftbquests.py` 现在会打印每章「离中心最多几格」，并硬性要求 ≤ `MAX_FAR = 11` 格，
同时保留跨度（≤ 40）、最大行距（≤ 4.5）、坐标不重叠等检查。

* 12 章现在**全部**「离中心 ≤ 7.5 格」，一章最多一屏半就能看全
* 排版只改几何：任务内容、前置（701 条）、章节分组都没动，环检测仍为 0

## ① 兵器谱：10 把毕业兵器归回各自的兵器线（12 条线 → 8 条线）

现在按**配方来源**把它们归位（配方怎么来就排在哪条线尾）：

| 毕业兵器 | 合成来源 | 归入 |
